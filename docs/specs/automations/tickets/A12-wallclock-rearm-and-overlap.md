# A12 — 墙钟短段重算定时器 + 准点宽限 + agent 任务重叠跳过

Status: ready（等 #49 本轮 Codex/Bugbot 修复包整体完成后再实施）
Blocked by: #49 review-fix bundle（acec08e 及其 CI）
Track: 推到现有 code 分支 `feat/automations-v2`，不开新 PR

## 背景（真实场景）
- 用户定 40 天后的提醒：Node `setTimeout` 超过 2^31-1 ms 会被压成 1ms，调度器空转重挂。（Grok Bot 在 box 用 #49 真实代码复现：1.5 秒内重挂 1323 次；Codex P1 scheduler.ts:533 同一问题）
- Mac 合盖睡眠唤醒、VM 暂停、墙钟跳变：定时器只挂一次长延迟，按单调时钟计时，到点任务要等长连接重连或 wake 才补发。
- 真实定时器总会晚 1ms 以上，而准点判定是毫秒级精确相等：8 次准点触发里 7 次被标成「补跑」。（Bugbot High r4303497598）
- agent 任务跑得比周期长（我们不设时长上限），下一次 fire 到点时上一次还在跑，会叠跑并重复发帖。

## 用户决定（2026-10-18）
1. 定时器每段最多睡 30–60 秒，醒来按墙钟重算到期项；取代本轮修复包里「单段 ≤ 约 24 天分段 arm」的写法（若已落地则替换，不叠加两套）。
2. 准点宽限 60 秒：只决定是否标「补跑」；fire 时间晚于 nextFireAt 不超过 60 秒且没有更早的漏跑，就算准点，不加补跑标注。不改变「什么算错过」的语义（仍无固定宽限，24h 补跑上限不变）。
3. 同一 agent 任务上一次未结束时，本次到点：跳过本次并留痕（看板该条显示跳过、本地日志记录原定时间和原因，不发群消息刷屏）。不并发、不排队。
4. 已开始 fire key 集合只保留时间窗（例如 48h），过期即清，防止长期运行时内存缓慢增长。

## 验收
- 测试：40 天后的一次性任务，在模拟时钟下每段 ≤ 60s，挂定时器次数有上界，不出现 1ms 空转。
- 测试：墙钟前跳（模拟睡眠 2h），下一段醒来时 60 秒内补发到期项，补跑标注正确。
- 测试：真实定时器晚 50ms 和晚 59s 都不标补跑；晚 61s 且确实错过则按补跑处理。
- 测试：agent 任务 run 未结算时下一次 fire 被跳过，日志和看板留痕，`lastStatus` 不被覆盖。
- 测试：fire key 超出时间窗后被清理。
- 现有调度/补跑/A8 结算测试全绿；push 和 PR 两次 CI 在 macOS/Ubuntu/Windows 全绿。
- spec `docs/specs/automations.md` 同步更新：短段重算、60 秒准点宽限、重叠跳过。

## 不做
- 不引入第三方调度库（Grok Bot 对比 croner/bree/bullmq/Temporal 等后结论：不值得换）。
- 不依赖 systemd/cron（box 容器没有）。
