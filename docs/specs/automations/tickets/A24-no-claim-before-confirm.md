# A24 — 确认前不声称「已提交/已创建」：先校验提案再投递正文，失败原因并入同一条回复

Status: ready-for-agent
Severity: **medium**（A11 r5 2026-10-18 15:06 实测：bot 先说「已提交本群 agent 任务…」，紧接着又发「无法解析时间表。」；所有成功的提案在点「是」之前也被说成「已提交」，与 Spec §1「点「是」即生效」矛盾）
Blocked by: A23（同样改 `src/automations/proposal.ts` 的提示词）
Track: 推到现有 code 分支 `feat/automations-v2`（PR #49），**#49 合入前完成**，不开新 PR
Spec: [../../automations.md](../../automations.md) §3（自然语言：先校验、确认前措辞）、Solution（点「是」即生效）

## 场景（A11 r5，真实触发，2026-10-18 15:05–15:06 UTC+8）

群成员 @bot「今天 15:50 运行一次 …」。15:06:00 bot 先发出 agent 正文 om_…8dc6「已提交本群 agent 任务「R4空结果」：今天 15:50 运行一次…」，随后才发 om_…931d「无法解析时间表。」。用户先被告知任务已提交，再看到一条没有上下文的失败。

同样的措辞出现在**每一次成功**的提案上：A11 第一次运行时用户只说「只需创建提醒」，Grok 也回「已提交本群定时提醒…」。任务要等有人点「是」才生效，正文却说已经提交。

## 触发

- 失败：任何被 bridge 拒绝的提案（例如 A23 之前的「今天 HH:MM」、低于下限、超过 1 年）。
- 误导：任何成功的提案（确认卡发出、尚未点「是」）。

## 根因（`5552726`）

1. **先发正文、后校验**：`src/bot/channel.ts` 的最终回复流程中，`applyAutomationProposal` 定义在 `:2509-2518`；校验和建 draft 在 `submitAutomationProposal`（`command.ts:418-512`，拒绝在 `:446-449`），它在正文投递**之后**才执行（`:2578` / `:2606` / `:2629`；正文在 `:2582` 的 `settleStreamDelivery` 发出）。正文发出时 bridge 还不知道提案是否合法。
2. **「已提交」是模型写的**：bridge 没有生成这句话；`proposal.ts:14-20` 只说「不要把该块当作给用户看的正文」，没有规定确认前的措辞。这是模型的默认习惯，不是测试用语带出来的。
3. **拒绝消息没有上下文**：`command.ts:448` 单独发一条「无法解析时间表。」，不带原始时间表和可用写法。

## 要做

- **先校验、后投递**：在投递最终回复正文**之前**，用纯函数（`parseScheduleText` + 下限 / 上限 / 任务类型校验，与 `submitAutomationProposal` 共用同一实现）校验提案。校验通过后再建 draft、发确认卡；正文的投递时机按下面两条决定附加内容。
- **失败**：在**同一条回复**正文末尾追加一行拒绝原因，含原始时间表和一个可用示例，例如「⚠️ 没有创建任务：无法解析时间表「今天 15:50」。可写成「明天 09:00」「2026-10-18 15:50」「10 分钟后」。」。不再另发独立的「无法解析时间表。」。不建 draft、不发确认卡。`auto.rejected` 按 A23 (d) 写。
- **成功**：bridge 在正文末尾追加固定一行「已生成确认卡，点「是」后生效。」（bridge 写，不依赖模型）。
- **提示词**（`proposal.ts:14-20`）：加一句「正文不要说已创建 / 已提交 / 已设置；任务要等群里有人在确认卡点「是」后才生效。」。
- **兜底**：即使模型仍写了「已提交 / 已创建 / 已设置」，bridge 追加的那一行也必须出现；不做正文改写（不删模型原话），在 PR 说明里写明。
- 流式卡路径（正文通过流式卡结算）与纯文本路径都要覆盖；追加行进入最终结算的同一张卡 / 同一条消息，不另发消息。
- 正文为空（模型只输出了提案块）时，回复就是追加的那一行（成功或失败原因）。

## 验收

- [ ] 先写失败测试（channel 级，recording channel + scripted CLI）：
  - 非法提案：群里只有**一条**回复，正文含拒绝原因（含原始时间表与示例），不含「已提交」「已创建」「已设置」（模型原话里没有时）；没有独立的「无法解析时间表。」消息；没有确认卡；有 `auto.rejected`。
  - 合法提案：回复末尾有「已生成确认卡，点「是」后生效。」；确认卡在回复之后发出；回复与确认卡各一条。
  - 顺序：校验发生在正文投递之前（断言投递时附加内容已确定）。
  - 流式卡路径与纯文本路径各一组。
  - 只有提案块、正文为空：回复就是追加行。
- [ ] 提示词快照测试：包含「不要说已创建 / 已提交 / 已设置」的约束。
- [ ] `pnpm ci:local` 绿；push 和 PR 两次 CI 在 macOS/Ubuntu/Windows 全绿。
- [ ] Bot Arena 实测（A11）：@bot 创建一个合法提醒 → 回复末尾是「已生成确认卡，点「是」后生效。」，确认卡随后出现；@bot 用一个非法时间表（例如「今天 <已过时刻>」）→ 只有一条回复，原因在回复里，没有独立的拒绝消息，也没有「已提交」。
