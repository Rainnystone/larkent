# Task 10 — P10 生产 bridge 真实使用 UAT

**Status:** 待办
**Delivers:** 在生产 Grok bridge 上，以真实用户的自然语言和桌面客户端操作走完一组覆盖提醒、文档工作、新闻摘要与各类排期的日常任务，留下卡片、存储、文档 revision 与 Monitor 日志四类证据，并在结束时清理干净。
**Blocked by:** [P09](P09-real-feishu-acceptance.md) 完成；#52 已合并，且由 Coder 部署到生产 bridge（`main`）
**Type:** UAT（用户验收测试）
**Worker class:** judgment

## What to build

P09 用脚本化 E2E 证明契约成立；本票验证“像真实用户一样使用”时同样成立。UAT Tester 以用户身份在飞书桌面客户端里用自然语言下达任务、点击卡片、阅读回复与文档，判断结果是否符合一个普通用户的预期。

设计原则是**少用 agent、覆盖面宽**：每条句子同时覆盖多个维度（CLI、排期类型、任务类型、管理操作），全程计划触发总数控制在约 10–14 次，短间隔只用于当天，长周期任务在首次触发验证后即取消，同一条线索复用同一篇文档，不因“想再看一次”而重跑；只有失败修复后才复验。

## 测试角色

| 角色 | 是谁 | 职责与边界 |
| --- | --- | --- |
| UAT Tester | agent 侧测试者，经 computer use 操作飞书桌面客户端 | 以用户身份发送下表句子、点击确认/删除/补全卡片、截图和阅读文档；按真实用户口吻输入，不贴命令语法 |
| 断言脚本 | lark-cli 的 `e2e-tester` profile | 只用于读取消息、卡片、文档与做脚本化核对；若需发消息，正文必须以 `【端到端测试】` 开头，且不得代替 UAT Tester 下达任务或点击卡片 |
| 生产 bridge | 部署在 `main` 的生产 Grok bridge | 被测对象；不为本票改配置、改代码或重启（部署由 Coder 负责） |
| larkent-monitor | 生产 bridge 的监控 | 被观察对象：核对它在计划触发时的 push/wake 行为与日志 |
| 用户 | 本人 | 仅在不可抗力时介入（客户端掉登录、权限弹窗、设备异常等），不承担日常点击 |

不使用 Test Bot（它不被 Monitor 覆盖，本票的价值之一是验证有监控的生产链路）。

## Boundaries

- 环境：生产 Grok bridge（`main`），专用测试话题群中的指定话题 `<uat-topic>`。公开记录只写占位符，不写群名、chat id、话题 id、人名、账号或 token。
- 文档：全部放在“指定的测试专用知识库空间”`<test-wiki>`，不在其他空间创建或修改文档；公开记录只写文档标题与占位符。
- CLI：主力为 Grok Build；Gemini（哈基米）因配额只用 2 条句子（S03、S10）；**任何时候不使用 Opus**。CLI 切换使用 bridge 既有的会话/话题切换方式，切换动作与生效证据一并记录，用完立即切回 Grok Build。
- 排期模型按[规格 D6](../../bridge-skills.md)：一次性、每日、工作日、指定星期、固定间隔（带时间窗口）；循环任务 `startAt` 包含、`endAt` 不包含；缺少结束边界返回 needs-input 卡片，不猜无限期、不把准确时刻改成窗口。
- 触发时间彼此错开（间隔 ≥10 分钟），避免两条任务同时运行导致证据混淆。
- 不新增凭据、不改 profile 认证配置、不跨群操作。发现缺陷时按 P01–P09 的流程修复并部署，本票只复验受影响句子。

## 时间线约定

`D` 为 UAT 开始日（Asia/Shanghai），须为周一至周四，使 `D+1` 为工作日。下表“发送”列为建议时刻，执行时可整体平移，但须保持相对顺序与错开间隔，并在证据中记录实际日期时间（Asia/Shanghai）。

## Acceptance criteria

- [ ] 运行前记录生产 bridge 的来源（进程、加载的构建 SHA、启动时间）解析到包含 #52 的 `main` 部署版本；来源不明时不开始。
- [ ] S01–S14 全部由 UAT Tester 以自然语言在飞书桌面客户端发送；所有确认、删除、替换、补全卡片由 Tester 经 computer use 点击。用户仅在不可抗力时介入，介入原因如实记录。
- [ ] 每条句子的预览、卡片、存储与实际触发次数一致：S04 恰好 3 次且 15:00 不触发；S05 两天各一次且替换后只按 08:30 触发；S06 补全前无任务、补全后 2 次；S07 实际 0 次；S08 实际 1 次。
- [ ] 回复区分等待确认、已保存、已执行完成与执行失败，没有提前宣称成功。
- [ ] 管理操作（S09–S12、S14）先查询当前目标与 revision，只作用于本话题任务，不误伤其他任务。
- [ ] 文档工作全部发生在 `<test-wiki>`；S05、S06 的多次追加落在同一篇文档；S13 移动后后续追加仍命中原文档。
- [ ] 10 次计划触发中每一次都有对应的 larkent-monitor 可观察记录（push/wake 或等价日志），且与触发时刻、任务对应；Monitor 缺失或延迟的触发单独列出。
- [ ] Gemini 只用于 S03、S10；全程未使用 Opus；未使用 Test Bot。
- [ ] 公开记录不含飞书 ID、群名、话题名、chat id、人名、token；敏感证据只留在私有环境。
- [ ] 清理完成：automation 列表为空，测试文档在 `<test-wiki>` 内归档，残留与未验证项逐条说明。

## Verification loop

1. 确认 Blocked by 全部满足，核对生产 bridge 来源与 Monitor 运行状态，记录 D 的实际日期与时区。
2. 按“发送”列顺序执行 S01–S14；每条发送后截图回复与卡片，点击卡片后再截图，并用 `e2e-tester` 脚本读取存储与文档 revision 做核对。
3. 每次计划触发后核对四类证据：飞书投递、存储状态迁移、文档 revision（如适用）、Monitor 记录。失败即停在该句，修复部署后只复验受影响句子与其后续触发。
4. S14 后执行清理：取消所有剩余 automation，确认列表为空；在 `<test-wiki>` 内归档 S02/S03/S13 涉及的文档；汇总每句 `pass` / `fail` / `unverified` 与证据位置。
