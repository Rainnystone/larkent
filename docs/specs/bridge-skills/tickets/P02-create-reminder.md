# Task 2 — P02 创建提醒、确认并可靠执行

**Status:** ready-for-agent · 待代码实施授权
**Delivers:** 用户用自然语言创建提醒，在本轮得到真实确认状态，点击既有确认卡后按准确排期执行；断线或重试不会重复创建任务和卡片。
**Blocked by:** [P01](P01-discover-and-preview.md)
**Worker class:** judgment

## What to build

把 P01 的结构化排期接入提醒创建、补全、确认、持久化和调度。首次引入写操作时同时交付操作编号、去重与恢复；不先交付可能重复写入的临时版本。复用现有草稿、确认及交付机制，不另建通用事务平台。

## Interfaces and boundaries

- 遵循[共同契约](README.md)与[规格 D6–D7](../../bridge-skills.md)。创建请求包含提醒类型、名称、正文、结构化排期和稳定操作编号；提供按编号查询结果。
- 客户端在提交前确定编号，超时响应仍携带它。相同编号与同一语义请求复用结果；不同内容冲突。定义编号过期和恢复规则，不能把已经过期的编号当新写入。
- 建立操作结果与现有草稿/任务/卡片的持久关联。人工 `/auto` 与新入口共用业务处理；收到请求、等待确认、已生效、已执行是不同状态。

## Acceptance criteria

- [ ] 完整链覆盖缺少结束时间的既有补全体验、排期预览、实际发卡、人类确认和真实调度触发；模型不能替用户确认。
- [ ] 固定时钟三天案例在预览、卡片、持久化及触发记录中一致，恰好三次且时间不漂移。
- [ ] 只有确认卡实际发送成功才返回等待确认；保存失败、发卡失败、链路离线及结果不明都如实返回，不提前声称已建立或已执行。
- [ ] 相同操作并发或重复提交只对应一个业务操作；不同内容复用编号、跨 profile/群查询和过期编号得到明确拒绝。
- [ ] 响应丢失后查询原编号能够恢复已知状态；投递结果确实不明时保持未知并进行可证明的核对，不盲目补发卡片或换编号重建。
- [ ] 重启仍可区分已应用、未应用和未知；保存与副作用之间的故障不会被当作一次全新操作。旧存储记录保持可读，不要求用户重建任务。
- [ ] run 取消只撤销后续调用资格，不伪装已接收操作被撤销；后续同归属合法 run 可查询原结果，旧凭据仍失效。

## Verification loop

1. 经完整消息链写失败回归：先发非法请求，再本轮修正，发卡确认并推进固定时钟观察执行。
2. 在实际持久化/投递边界注入故障、并发、断线和重启；通过真实客户端重查/重交原编号，断言草稿、任务、卡片数量和状态。
3. 验证原人工创建/补全/确认回归，运行相关 integration/process 测试与 `pnpm ci:local`。测试证据必须包含实际状态，不能只比对回复文案。
