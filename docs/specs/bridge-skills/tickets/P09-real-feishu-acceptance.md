# Task 9 — P09 真实飞书端到端验收（E2E，无 UAT）

**Status:** ready-for-agent · 待实施及相应真实测试授权
**Delivers:** 对同一候选版本给出真实飞书端到端证据：脚本化场景全部通过，可用的真实 CLI 各自留下业务证据，并准确列出未验证项。
**Blocked by:** [P08](P08-cutover-and-upgrade.md)
**Worker class:** judgment

## 范围：只做 E2E，不做 UAT

本票是端到端验收（E2E），不是用户验收测试（UAT）。

- 判定依据是脚本化场景的可观察结果：飞书消息与卡片、持久化状态、执行产物与回执，对照下文每条场景的期望结果。不以使用体验、主观满意度或开放式试用作为通过条件。
- 验收使用专用测试数据根、测试 profile 和测试群，全部用占位符表示；不使用生产群，不在公共记录中出现真实 ID、账号名、群名或凭据。
- 修复验收发现的范围内缺陷并复验。不把失败改记为通过，不缩小首版范围，不改平台无关 timeout，不新增凭据副本。
- 本票不授权合并、部署或重启任何线上 bridge。线上 bridge 及其 checkout、服务和数据根一律不碰。

## 测试角色

| 角色 | 是谁 | 职责与边界 |
| --- | --- | --- |
| E2E Tester | 执行脚本化场景的测试者 | 按场景步骤操作，记录输入、输出与状态；不临场改脚本，不代替确认 |
| Test Bot | 真实 CLI 本身 | 以被测 CLI 的真实进程运行，**不对其做监控或注入**；它的工具调用与回复是被观察的对象，不是被操控的对象 |
| 指定测试机器人账号 | 飞书侧的机器人账号 | 确认卡片只能由该账号点击。点击前先在测试群验证该账号确实拥有点击权限；未验证权限不得点击，也不由任何模型或个人账号代点 |

需要人类确认的既有动作保持为人类动作。Test Bot 返回的 operationId 只用于后续查询，不构成确认。

## 场景

公共前置：专用测试数据根 `<test-root>`、测试 profile `<test-profile>`、测试群 `<test-chat>`，均用占位符记录。每条 bridge 命令带相同的 `LARK_CHANNEL_HOME=<test-root>` 与 `--profile <test-profile>`。

### 场景 1 — 发现与真实工具回路（新会话 + 续会话）

- **步骤：** 初始上下文只含插件摘要。按用途发现 automation 与预装的良性纯 skill、脚本包；分别用明确唯一名称与有歧义的名称各查一次。用运行时既有工具执行声明的脚本并记录真实输出。查询 schema 与任务列表。观察 `lark-channel-bridge tool` 的请求经 JSON stdin 进入、结构化结果经 stdout 返回，诊断在 stderr。输入包含字面 Unicode、空格、引号与 shell 字符。保持现有访问模式与原生插件配置不变。
- **期望：** 摘要之外的正文按需读取；歧义时返回候选而不猜测；脚本输出与实际执行一致；stdout 只有一份协议结果。
- **证据：** 每个 CLI × 新/续会话各一份：输入文本、工具请求与结果、脚本真实输出、飞书回复。
- **覆盖：** A01、A02、A03、A06。

### 场景 2 — 同轮纠错与三天日程

- **步骤：** 对无副作用的预览故意漏掉必填结束边界，或提交一个非法参数；在同一轮拿到具体错误并修正，保持 09:00 与原始意图。续会话再做一次。真实环境选择未来本地日期 D，明确要求 D、D+1、D+2 每天 09:00，排他结束于 D+3 00:00，记录实际日期与时区。历史日期回归（2026-10-19 09:00 前的固定时钟 → 10 月 19/20/21 日 09:00，恰好三次，排他结束 10 月 22 日 00:00）只在自动化固定时钟下运行，绝不在真实环境创建过去的任务。
- **期望：** 非法预览无任何副作用；修正后的规范化预览、确认卡片、持久化日程与计划触发次数一致，恰好三次。不为通过而改成时间窗口。
- **证据：** 错误文本、同轮修正后的预览、卡片与存储内容的对照。
- **覆盖：** A08、A09。

### 场景 3 — 人工确认与状态迁移

- **步骤：** 经共享工具创建提醒与 agent 任务，保留返回的 operationId。确认卡片由指定测试机器人账号点击，点击前按测试角色一节验证点击权限。随后查询回执。三天提醒与用于观察实际触发的近期 agent 任务分开；三天提醒的真实投递只在实际发生时记录，未到期不记通过。
- **期望：** `waiting-confirmation` 对应一张实际送达的卡片；`applied` 只表示已保存，不表示已触发或已投递。创建、确认、派发、执行成功/失败、投递各自独立可核验。
- **证据：** 卡片消息、点击主体、任务与 revision 状态、回执查询结果；至少一条可观察的自动执行及其输出。
- **覆盖：** A10、A11。

### 场景 4 — 管理与恢复

- **步骤：** 替换、删除、暂停、恢复前先查询当前目标 ID 与 revision。工具侧替换与删除需要真实人工确认；暂停、恢复与看板操作沿用既有规则。用过期 revision 和已删除目标各试一次。对一次结果不确定的操作，在同 profile、同群的后续合法 run 中按原 operationId 查询，不另起新 ID 重建。
- **期望：** 过期 revision 与已删除目标失败且不影响其他任务；一次不确定结果不产生重复卡片或任务，也不出现隐藏的成功。
- **证据：** 每次操作前后的查询结果与任务列表差异。
- **覆盖：** A12（查询先行、不盲目重发）。

### 场景 5 — 自动身份与生命周期

- **步骤：** 用与人工会话相同的 profile 各做一次允许的 bot 操作和一次已授权的 user 操作。创建者与该 profile 的授权主体不同，只记录公开标签并在私有环境核对。构造一次授权失败。自动 run 中发起认证或配置变更请求。自动 run 期间尝试递归的创建、替换、删除、暂停、恢复。停止一个受控的活动 run，再用后续合法 run 查询其已接受的操作。
- **期望：** 授权失败如实报告且不借用其他凭据；认证/配置变更请求被拒绝或中断并返回 `auth-config`，线上凭据无变化；管理工具在自动 run 中被拒绝，插件读取与业务工作仍可用；停止后原连接失效，已接受的业务操作仍可查询且不被取消。
- **证据：** 两类操作的身份标签、失败文本、`auth-config` 结果、停止前后的连接与查询结果。
- **覆盖：** A07、A13、A14。

### 场景 6 — lark-cli 依赖

- **步骤：** 记录实际安装的 lark-cli 版本及其 `lark-channel` 绑定支持。核对人工 run 与自动 run 使用同一 profile 本地配置与凭据存储、存储属主可写。在该操作系统与该存储上、于批准的受控条件下核验原生的跨进程刷新锁与回写。
- **期望：** bridge 不复制 token、不独立刷新、不改写身份环境。P03 的隔离环境版本核验只作参照，不算本环境证据。
- **证据：** 版本与绑定能力输出、存储属主、锁与回写的观察记录。做不到的项记为未验证，不安装凭据、不放宽范围。
- **覆盖：** A13 的真实依赖部分。

### 场景 7 — 升级路径（v1 → 候选，仅测试 bridge）

本场景使用两个独立的 git worktree，只供测试 bridge 运行。线上 bridge 及其 checkout、服务和数据根始终不碰、不拉取、不构建、不重启。

- **旧版本 worktree：** 当前 `master` 的 `953e7bd`（#52 之前交付的版本，automation 存储为 schema v1，也是固定夹具 `pre-tools-v1.json` 的导出来源）。`git worktree add --detach <test-dir>/p09-old 953e7bdde3549b03bddb8d191d8856683d1dc4c5`
- **新版本 worktree：** PR 分支 `feat/bridge-skills`，固定到候选 SHA（当前 `08102d4`；评审修复推进 HEAD 后重新固定）。`git worktree add --detach <test-dir>/p09-new <candidate-sha>`
- 两个 worktree 各自安装并构建（`pnpm install --frozen-lockfile && pnpm build`），分别记录 `git rev-parse HEAD`。
- **启动前隔离检查：** 选专用测试数据根与测试 profile，每条命令带相同的 `LARK_CHANNEL_HOME=<test-root>` 和 `--profile <test-profile>`。用 `ps` 与 `status` 确认没有线上 profile 使用该数据根，且该测试 profile 没有从其他 checkout 或系统服务运行。使用前台 `run` 而不是 `start`，避免安装或改写 per-profile 服务。
- **阶段 A（旧版本）：** 在 `p09-old` 运行 `LARK_CHANNEL_HOME=<test-root> node bin/lark-channel-bridge.mjs run --profile <test-profile>`。记录运行来源：worktree 路径、SHA、pid 与启动时间。在测试群经旧的 `/auto` 流程造出真实 v1 数据：一条已保存提醒、一条已保存 agent 任务；未点击的创建、删除、替换确认卡片各一张；一份未填写结束日期的未完成周期性草稿；看板；一张已点击卡片以留下已吊销 nonce。条件允许时再留一条已暂存到 outbox 的回复更正。确认该 profile 的 `automations.json` 为 schema v1。
- **切换：** Ctrl-C 停止并等待干净退出，用 `ps` 确认无残留进程。对整个测试 profile 目录做私有配套备份并记录校验和。
- **阶段 B（新版本）：** 在 `p09-new` 用相同的 `LARK_CHANNEL_HOME`、相同 profile、**同一个数据目录**重启测试 bridge。不清空存储、不重建任务、不启用兼容开关。再次记录运行来源并确认解析到候选 SHA。核验：
  - `automations.json` 原地升级到 v2，任务、草稿、看板绑定与 nonce 历史全部保留。
  - 人类点击原签名卡片仍然生效，已吊销 nonce 仍被拒绝。
  - 补全周期性草稿的结束日期需要单独一次人工确认。
  - 已保存任务保持原日程并照常触发。
  - 旧会话可以续上。
  - 单独的旧回复标签不产生任何操作；工具调用与旧标签混合的回复恰好执行一个操作。
  - outbox 中已暂存的投递或撤回可以完成，且不重发、不发起新的模型操作。
  - 身份配置与 lark-cli 凭据保持不变。
- **期望：** 升级后的数据与阶段 A 备份逐项对应，除 schema 版本与升级本身引入的字段外无差异。
- **证据：** 两阶段的来源记录、v1 与 v2 存储的对照（脱敏）、卡片点击与 nonce 结果、续会话与混合回复的观察。
- **覆盖：** A05、A15。
- **回退与清理：** 仅把代码切回 `p09-old` 不会降级已升级的数据，回退前先恢复阶段 A 的备份。证据记录完成后，经人工确认暂停或删除测试任务，再 `git worktree remove` 两个 worktree，并报告全部残留。

## 故障注入

注入只在隔离的测试数据上进行；破坏性存储/传输失败优先引用既有自动化证据，除非某项现场失败测试被单独批准。

| # | 注入方式 | 期望 | 覆盖 |
| --- | --- | --- | --- |
| F1 | 预览提交非法参数或缺字段 | 具体错误、同轮可修正、无副作用 | A08 |
| F2 | 用过期 revision 或已删除目标做替换/删除 | 失败，其他任务不受影响 | A12 |
| F3 | 结果不确定后用新 operationId 重试（反例，预期被阻止） | 不产生第二张卡片或第二个任务；原 ID 仍可查询 | A11、A12 |
| F4 | 自动 run 中请求认证/配置变更 | 拒绝或中断，返回 `auth-config`，凭据无变化 | A13 |
| F5 | 自动 run 中递归调用管理工具 | 管理操作被拒绝，读取与业务工作可用 | A07 |
| F6 | 停止活动 run 后用原连接再调用 | 连接已失效；此前已接受的操作仍可经后续合法 run 查询 | A12 |
| F7 | 卡片回读时不带 `card_msg_content_type=user_card_content`，与带上该参数各取一次同一条卡片消息 | 不带参数时内容是降级/回退形态，签名回调 token 不可见或不可比；带上参数时正文为 schema 2.0 卡片本身，能取到与原卡片一致的回调 token。回读对账必须以带该参数的结果为准，缺 token 不得当作未送达的证据 | A11 |

F7 的原因：CardKit 2.0 的消息内容在不带 `card_msg_content_type=user_card_content` 时返回的是兼容回退，签名回调 token 位于 schema 2.0 正文中。用回退内容做 token 比对会把已送达误判为未送达，因此该参数是回读路径的必查项。

## 话题群

- 测试群 `<test-chat>` 使用一个指定话题 `<test-topic>`。群组与话题两类容器都要覆盖，不把群级结果当作话题级通过。

## 证据与结论

每条场景报告 `pass`、`fail` 或 `unverified`，并附：候选 SHA 与实际运行 SHA、时间与时区、CLI/模型/版本/操作系统、会话模式、脱敏的输入与结果、观察到的卡片/任务/回执/执行/投递状态、证据位置。

- 真实 ID、账号名、群名、token、回调凭据与原始私有日志不进入公开评论与本仓库；公开记录只用占位符与场景编号，敏感材料只留在批准的私有环境。
- 全部必验场景通过、三个待验收 CLI 的新/续会话完成、失败项修复并复验后，本票才算完成。Codex、Claude Code、Kimi 明确保持未验证，不阻断结论的诚实性，但不得被表述为已通过。
