## Logged fields on `agent` `terminal-result`

Every Antigravity `terminal-result` log entry in `src/agent/antigravity/jsonl.ts` (`AntigravityJsonlTranslator.logTerminalResult`) now records four terminal facts alongside existing metadata (`status`, `errorCode`, `errorType`, `errorMessage`, `conversationId`, `numTurns`), logging lengths/enums only and never reply content:

- `finished_reason`: `string | null` — `result.finished_reason` when non-empty (`"error"`, `"print_timeout"`, `"interrupted"`), or `null` when omitted (such as `SUCCESS` in `agy` 1.5.x, which uses `omitempty`).
- `responseChars`: `number` — `result.response.length` when `result.response` is a string, else `0`.
- `heldAnswerChars`: `number` — `FinalAnswerCore.pendingLength()` at terminal time (before `complete()` flushes/clears `pending`).
- `lastStepType`: `string | null` — `step_type` of the last `step_update` seen before `result` (`"agent_response"`, `"error_message"`, `"tool"`, `"system_message"`, `"user_input"`, `"checkpoint"`), or `null` when `result` arrived without prior `step_update` events.

## Which field carries the answer on an ERROR-with-answer turn?

**Both `result.response` and held-back `agent_response` text (`FinalAnswerCore` `pending`) carry the exact same full text on real `agy` ERROR-with-answer turns.**

### Evidence from real `agy` captures and 2026-11-13 incident databases

1. **Sticky error on a resumed conversation where the turn answered (`tests/fixtures/antigravity/error-with-response.jsonl`, from `rt1` capture `stdout-agy-288d45af`)**:
   - `step_update` step 7 (`agent_response` `ACTIVE` `"PONG-01"` + `DONE` `"\n"`) accumulated `8` held chars.
   - `result` emitted `{"status":"ERROR","response":"PONG-01\n","error":"failed to construct executor: unknown model key MODEL_PLACEHOLDER_M418: model not found","finished_reason":"error"}` (`responseChars: 8`, `heldAnswerChars: 8`, `lastStepType: "agent_response"`).
2. **`print_timeout` with an open background tool (`tests/fixtures/antigravity/print-timeout-open-tool.jsonl`)**:
   - `step_update` step 6 (`agent_response`) and `result.response` both contain the exact same `101`-char string (`responseChars: 101`, `heldAnswerChars: 101`, `finished_reason: "print_timeout"`, `lastStepType: "agent_response"`).
3. **Mid-turn interim narration followed by upstream network failure (`tests/fixtures/antigravity/error-interim-narration.jsonl`, from `rt1` capture `stdout-agy-bcafc5d7`)**:
   - `step_update` step 6 (`agent_response`) and `result.response` both contain the exact same `48`-char interim message (`"后台任务已启动（Task ID: `task-5`），正在等待命令执行完成。完成后将更新结果。\n"`), followed by `system_message` (step 7) and nine `error_message` steps (steps 8–16), ending with `status: "ERROR"`, `finished_reason: "error"`, `responseChars: 48`, `heldAnswerChars: 48`, `lastStepType: "error_message"`.
4. **Why both match**:
   - `agy -p --output-format stream-json` concatenates every `agent_response` `text_delta` emitted during the invocation (including pre-tool narration and final answer) into `result.response` (also seen in `tests/fixtures/transcripts/antigravity/narration-tool-answer.jsonl`).
   - `AntigravityJsonlTranslator` intentionally skips `{ type: 'boundary' }` on `tool` steps (`src/agent/antigravity/jsonl.ts`), so `FinalAnswerCore` (`accumulation: 'delta'`) accumulates the exact same `text_delta` sequence into `pending`.
   - Using `result.response` with fallback to `pending` (the exact `input.content ?? this.pending` path `FinalAnswerCore.complete()` already uses on `SUCCESS`) handles both real `agy` streams and synthetic/partial streams where one side is empty.

## Why `lastStepType` was added (and what Tickets 02 and 03 must know)

1. **`responseChars > 0` / `heldAnswerChars > 0` alone is NOT sufficient to prove the turn finished an answer**:
   - Because `agy` concatenates pre-tool / pre-wakeup narration into `result.response` and `pending`, a turn that emitted interim narration ("background task started, waiting...") and then genuinely failed (`error-interim-narration.jsonl`, `bcafc5d7`) has `status: "ERROR"`, `finished_reason: "error"`, `responseChars: 48`, `heldAnswerChars: 48` — identical in the three suggested fields to a sticky-error turn that completed its answer (`error-with-response.jsonl`, `288d45af`, and the 2026-11-13 `cursor` incidents `939b4832` at 15:14 and `b4314394` at 15:46 where an earlier step recorded an `error_message`, `agy` recovered across subsequent tool steps, and finished on a `DONE` `agent_response` with exit code `0` and no `AGY_ERROR` on stderr).
   - `lastStepType` separates them on the single `terminal-result` log line: genuine sticky-ERROR-with-finished-answer runs end on `lastStepType: "agent_response"` with `finished_reason: "error"`, whereas mid-turn failures after interim narration end on `lastStepType: "error_message"` (and `print_timeout` has `finished_reason: "print_timeout"`, `interrupted` has `finished_reason: "interrupted"` / `lastStepType: "tool"`).
2. **Caveats for Ticket 02 (`02-error-with-answer-delivers`)**:
   - **Check scrubbed answer non-emptiness**: `responseChars` and `heldAnswerChars` measure raw protocol lengths before `scrubSystemMessageEnvelopes`. An envelope-only `<SYSTEM_MESSAGE>` / `<task_notification>` payload has `responseChars > 0` raw but scrubs to `""`. Ticket 02 must run envelope scrubbing (`clean`) before deciding a non-empty answer exists.
   - **Guard against non-answer terminal states**:
     - Require `finished_reason !== 'print_timeout'` and `finished_reason !== 'interrupted'` (those keep their existing handling and resumability).
     - Require `lastStepType === 'agent_response'` (and ensure the trailing `agent_response` segment after the last non-`agent_response` step actually carried answer text and completed `DONE` with no open tools, since `agy` also emits delta-less `agent_response` steps for thinking-only tool planning).
   - **Sticky conversation poisoning still applies**: Even when Ticket 02 delivers the completed answer on a sticky `ERROR` turn (`939b4832`, `b4314394`, `288d45af`), that `conversationId` remains poisoned in `agy`'s SQLite DB — every future `--resume <conversationId>` will continue returning `status: "ERROR"`. Ticket 02 must still invalidate/rotate the resume handle (or avoid persisting the poisoned handle for subsequent turns) while delivering the answer cleanly.
3. **Caveats for Ticket 03 (`03-error-without-answer-reruns-once`)**:
   - Pre-attachment CLI errors (e.g., invalid `--model`, `conversationId` absent, `numTurns: 0`, `lastStepType: null`) never attached to a conversation and will fail deterministically if rerun with the same arguments; distinguish sticky/transient resume errors (`9886c107` / network / poisoned-session errors with `responseChars === 0` or `lastStepType === 'error_message'`) from deterministic config/flag errors if applicable.
