## How the single automatic fresh rerun is chosen

Shared-layer recovery is keyed strictly on generic terminal/outcome facts — never on `agentId === 'antigravity'`:

1. **`RunOutcome.sessionDiscarded` (`src/bot/run-outcome.ts`) & global `继续` suppression (`src/bot/interruption-notice.ts`)**:
   - `deriveRunOutcome` sets `sessionDiscarded: true` on `RunOutcome` whenever `input.terminalEvent` carries `invalidateResume` (`invalidatedResumeHandle(input.terminalEvent)` is truthy).
   - `planInterruptionNotice(outcome)` returns `{ kind: 'none' }` whenever `outcome.sessionDiscarded` is `true` on any outcome that would otherwise plan `{ kind: 'continue' }` (`partial`, `interrupted`, `failed`), while preserving `{ kind: 'auth' }` for `auth-required`.
   - Because `Outbox.deliverFinalReply`, `Outbox.deliverNotice`, and startup crash recovery (`onInterrupted` in `src/bot/channel.ts`) all route through `planInterruptionNotice`, **no path ever offers a `继续` card when a terminal carried `invalidateResume`**, whereas `print_timeout` and `interrupted` (which omit `invalidateResume`) keep their existing session handle and `继续` card untouched.

2. **Eligibility gate for the one automatic chat rerun (`shouldAutoRerunDiscardedError` in `src/bot/turn.ts`)**:
   - Ticket 02 already converts sticky `ERROR`/`FAILED` turns that finished an answer into `{ type: 'done', terminationReason: 'normal', invalidateResume }`. Any turn still arriving with `{ type: 'error', terminationReason: 'failed', invalidateResume }` genuinely has no completed answer and had an attached conversation handle that has just been discarded in `SessionStore`, `SessionCatalog`, and `TurnJournal`.
   - `deliverChatTurn` suppresses Attempt 1's failure delivery and returns `autoRerunOutcome` to `runAgentBatch` (`src/bot/channel.ts`) if and only if **all** of these hold:
     1. `delivery.autoRerunOnSessionDiscard === true` (`true` on Attempt 1 of a chat turn, `false` on Attempt 2 — bounding automatic reruns to **at most one** per user batch).
     2. `!handle.stopRequest && !handle.interrupted` (user `/stop`, superseding `/new`/`/cd`/`/ws`/`/resume`, policy guard, or external signal was not requested).
     3. `terminalEvent?.type === 'error' && terminalEvent.terminationReason === 'failed' && Boolean(terminalEvent.invalidateResume)` (attached no-answer `ERROR`/`FAILED` regardless of `agy`'s `retryable` flag; excludes pre-attachment CLI errors such as invalid `--model`, runner kills, non-zero exits without `result`, and spawn errors, none of which carry `invalidateResume`).
     4. `outcome.kind === 'failed' && !outcome.needsHuman` (excludes `auth-required` / `cli-missing`).
     5. `delivery.canRecordSession?.() !== false` and the journal entry is not `'voided'` (a concurrent superseding session switch did not invalidate the writer).
   - When Attempt 1 is suppressed for auto-rerun:
     - `processAgentStream` logs `log.info('turn', 'auto-rerun-scheduled', { scope, outcome })` instead of `card.final` and skips terminal state flush so an opened progress card never flashes `⚠️ agent 失败`.
     - `awaitRenderAwareStream` skips the 3 s post-run grace wait (`suppressed: () => Boolean(autoRerunOutcome)`), abandoning an unstarted stream or awaiting an already-started producer so `outbox.recallStream` (`recallStreamedReply` in `src/bot/outbox-reply.ts`) recalls any mid-turn progress card cleanly.
     - Attempt 1's `TurnJournal` entry is voided (`journal.voidTurn(turnId)`), and `outbox.deliverFinalReply` is skipped.

3. **Fresh-session rerun execution (`runAgentBatch` in `src/bot/channel.ts`)**:
   - Guarded by `!deps.isClosing?.() && deps.canRecordSession()` (re-checked after fetching `topicContext` if Attempt 1 in a topic thread had skipped `topicContext` because `topicResumeHandle` was set before being discarded).
   - Rebuilds the prompt with `[continueExtraInstruction(firstResult.autoRerunOutcome, userInputText), ...sharedExtraInstructions]` (`CONTINUE_HINT`: inspect workspace state / completed steps first and do not repeat side effects, without carrying over a consumed one-shot `taken` instruction from before Attempt 1), logs `log.info('turn', 'auto-rerun', { scope, outcome, promptChars })`, and calls `runChatAttempt` once with `forceResumeHandle: null` and `isAutoRerun: true` inside the same `sessionWriter` / `pending` scope lock.
   - Because Attempt 2 runs inside `executeTurn` with its own `RunHandle` and `TurnJournal` entry under the same `scope`, `/stop`, superseding `/new`/`/cd`/`/ws`/`/resume`, and queued follow-up messages during the rerun behave identically to a normal run.

## How a second failure is shown

- On Attempt 2 (`isAutoRerun: true`, `autoRerunOnSessionDiscard: false`):
  - `shouldAutoRerunDiscardedError` returns `false`, so **no third run** can ever start.
  - Attempt 2 flows through normal terminal rendering and `outbox.deliverFinalReply`: one error reply (`⚠️ agent 失败：...`, plus `下一条消息将开始新会话` whenever Attempt 2's terminal also carried `invalidateResume`) is delivered.
  - `planInterruptionNotice` suppresses `继续` via `outcome.sessionDiscarded: true` when Attempt 2 attached and discarded its session, and `effectiveNotice()` in `deliverChatTurn` also omits `notice` on any non-`auth-required` `failed` outcome when `delivery.isAutoRerun` is `true` so even a pre-attachment failure on Attempt 2 never emits a `继续` card.

## What later work (including Ticket 04) must know

1. **Typing reaction lifecycle across auto-rerun (`04-typing-reaction-left-behind`)**:
   - In `text` and `markdown` modes (`cotEnabled === false && replyMode !== 'card'`), `deliverChatTurn` adds a working reaction at the start of an attempt and schedules `scheduleWorkingReactionCleanup(channel, lastMsg.messageId, reactionPromise)` in `finally`. During an auto-rerun, Attempt 1's `finally` schedules cleanup of Attempt 1's reaction concurrently with Attempt 2 adding its own working reaction on the same `lastMsg.messageId`. `card` mode (`profiles.cursor` default) does not use `addWorkingReaction`, so normal `card` reruns are unaffected, but Ticket 04 should keep this two-attempt `text`/`markdown` sequence in mind when investigating reaction races.
2. **Observability signatures for auto-rerun**:
   - Attempt 1 logs `agent` `terminal-result` (`status: 'ERROR'`), `turn` `auto-rerun-scheduled`, and **no** `card` `final`.
   - Attempt 2 logs `turn` `auto-rerun`, `session` `fresh`, `agent` `terminal-result`, and the single `card` `final` for the user batch, followed by `flush` `end`.
3. **Document comments & automations**:
   - Auto-rerun is scoped to `ChatTurnDelivery` (`runAgentBatch`). Document comments (`src/bot/comments.ts`) and automations (`deliverAutomationTurn`) remain single-attempt; comments still discard `invalidateResume` handles and append `下一条消息将开始新会话` on `error`.
