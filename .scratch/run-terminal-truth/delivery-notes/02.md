1. `keeps resuming the same conversation after an agy SUCCESS` — `Error: timed out` at `waitFor` line 86 (`resumeFor('oc_dm', h.cwd, 'antigravity') === 'sess-agy'`), ~2056 ms. That is the helper’s 2 s `performance.now()` deadline, not the 20 s describe timeout.
2. `keeps a non-agy adapter error session` — `expected undefined to be 'sess-claude'` at line 141 (`resumeFor('oc_dm', h.cwd, 'claude')`).

`SessionStore.resumeFor` returns the handle only when `scoped.cwd === cwd`. The product stores `policy.cwdRealpath` from `resolveWorkingDirectory` (`fs.realpath`). The harness queried `tmp.workspace`. On Linux those strings match (`/tmp/...`). On macOS `/var/folders` vs `/private/var/folders`, and on Windows a short/junction temp path vs the canonical path, they do not, so a stored SUCCESS/claude handle looks missing. The ERROR case’s `resumeFor` `toBeUndefined()` was a false green on the same mismatch; catalog + next-run argv still proved discard. Bumping `waitFor` would not help: the predicate is never true.

Fix (`cdda0382`): requested workspace is a dir symlink/junction; lookups use `realpath(requestedCwd)`. Expects stay `'sess-agy'` / `'sess-claude'`. No timeout change.

## What landed

- Antigravity JSONL maps CLI `result.status` ERROR/FAILED to a terminal `error` with adapter-declared `invalidateResume: true`. Translator `fail()` / `finish('failed')` omit the field (runner / print-timeout / stream-ended errors keep ticket 09 continue-resume).
- Shared `recordRunSessionEvent` keys off that field, not `agentId === 'antigravity'`. On `invalidateResume` it clears SessionStore (session-resume CLIs) and archives the matching SessionCatalog active entry. Other adapters omit the field and keep today's resume-on-error behaviour.
- Chat turn recording also clears the turn-journal `resumeHandle`, so 继续 / `forceResumeHandle` does not pass the poisoned conversation id. The next message starts a fresh agy conversation (no `--conversation`).
- Current-turn outcome is unchanged: a genuine CLI ERROR still settles `failed` with `agent 失败`. The failure notice appends `下一条消息将开始新会话`. No "text + exit 0 means success" heuristic (D1). Sticky historical errors are not reclassified.

## Diagnosis gate (kept; D2 amendment used option a)

2026-11-09, local agy, fresh session, worktree `/workspace/rt-agy-fix` @ `aabcefe6`, no product edits.

**Verdict at the time: no reliable current-turn error discriminator in agy 1.5.3 output.**

- `result.status` / `error` / `finished_reason` (even `duration_seconds`) stay sticky on a resumed turn that succeeds (PONG: reply `PONG-01`, exit 0, still `ERROR`). `result` has no error id or origin-turn field.
- An `error_message` step separates R2 from PONG, but it does not hold up as a rule: PING was a genuine current-turn error (turn 2, right after SEED SUCCESS) with `steps: []` (no `user_input` and no `error_message`). Eligibility failures on resume also emit zero steps.
- `AGY_ERROR` on stderr is not universal: PING's cascade-start timeout and the eligibility failures emit none.
- Rejected: using "non-empty response or exit 0 means historical" (a D1-forbidden heuristic), comparing `result.error` strings (would swallow genuine repeated errors), and `runId` / `num_turns` (these identify the turn, not which turn owns the error).
- Open: the sticky Bad Gateway captures lack full `step_update` lines, and it is untested whether a turn that streams early text and then fails sets both `response` and `ERROR`.

User decision (D2 amended 2026-11-09): do not reclassify; discard the resume handle after ERROR/FAILED (option a). Full finding: `/workspace/rt-e2e-evidence-20261109/round4/AGY-TICKET02-FINDING.md` (box evidence, not committed).
